1

Tujuan Dokumen Ini

Dokumen ini menjadi landasan (grounding) untuk penggunaan Codex saat menyusun BAB IV agar tetap konsisten dengan rumusan masalah, tujuan, batasan, kerangka konsep, dan hipotesis yang sudah disusun pada BAB I–III.

  • Menjaga narasi tetap berfokus pada apa yang dilakukan, bagaimana dilakukan, dan data yang dihasilkan.
  • Menghindari narasi baru yang tidak ada pada bab awal.
  • Menegaskan bahwa semua angka menggunakan placeholder, bukan data fiktif.
Prinsip utama: Output Codex wajib menjelaskan tahapan eksperimen dan keluarannya tanpa mengarang hasil.
2

Identitas Penelitian (Ringkas)

Fokus Penelitian

Analisis perbandingan kinerja algoritma konsensus Raft dan SmartBFT pada Hyperledger Fabric (permissioned blockchain), khususnya pada ordering service.

Rumusan Masalah Inti

  • Apakah terdapat perbedaan kinerja antara Raft dan SmartBFT pada skenario uji yang sebanding?

Tujuan Penelitian

  • Mengukur throughput, latency, resource usage, dan fault tolerance.
  • Menganalisis karakteristik kinerja berdasarkan mekanisme konsensus.
  • Menjelaskan implikasi pemilihan konsensus untuk Fabric.
3

Ruang Lingkup & Batasan

Batasan Wajib

  1. Platform hanya Hyperledger Fabric.
  2. Fokus pada ordering service (Raft vs SmartBFT).
  3. Beban menggunakan transaksi dummy (synthetic workload).
  4. Parameter evaluasi: throughput, latency, resource usage, fault tolerance.
  5. Tidak menambah metrik/variabel baru di luar BAB I–III.

Catatan Fault Tolerance

Analisis fault tolerance hanya berdasarkan skenario gangguan yang benar-benar diuji.

Jangan klaim pengujian fault tolerance luas jika tidak dilakukan.
4

Kerangka Konsep

Relasi sebab-akibat yang harus selalu muncul dalam pembahasan:

  • Konsensus Raft/SmartBFT diterapkan pada ordering service.
  • Ordering service mengelola pengurutan transaksi, batching, pembentukan blok, dan distribusi blok.
  • Perbedaan proses memengaruhi throughput, latency, resource usage, serta fault tolerance.
Pola pembahasan wajib: hasil → interpretasi teknis → kaitkan ke ordering service → simpulkan trade-off.
5

Hipotesis yang Harus Dijawab

H1 · Throughput

Terdapat perbedaan throughput antara Raft dan SmartBFT.

H2 · Latency

Terdapat perbedaan latency antara Raft dan SmartBFT.

H3 · Resource Usage

Terdapat perbedaan penggunaan CPU/memori antara Raft dan SmartBFT.

H4 · Fault Tolerance

Terdapat perbedaan karakteristik fault tolerance sesuai ruang lingkup pengujian.

6

Metode Penelitian

  • Jenis: eksperimen kuantitatif berbasis benchmarking.
  • Objek uji: Network A (Raft) dan Network B (SmartBFT).
  • Pengumpulan data melalui observasi dan pencatatan otomatis.
  • Parameter dicatat: throughput (TPS), latency, resource usage, fault tolerance.
7

Instrumentasi & Lingkungan Uji

Laptop

Digunakan untuk instalasi, konfigurasi, dan persiapan network config.

VPS Ubuntu 24.04 LTS

Menjalankan network uji serta eksperimen utama.

Jangan menyatakan semua pengujian dilakukan di laptop.

Arsitektur Sistem Pengujian

  • Dua jaringan terpisah: Network A (Raft) dan Network B (SmartBFT).
  • Parameter dasar setara untuk perbandingan adil.
  • Beban melalui dummy transactions.
  • Dummy dikirim via web prototype / transaction generator.
  • Data hasil berasal dari logging/monitoring.

Aturan Do / Don't

✅ Do

  • Gunakan alur eksperimen repeatable: skenario → setup → eksekusi → logging → grouping → analisis.
  • Tekankan fairness: beban identik, prosedur sama.
  • Hubungkan hasil ke ordering service.
  • Gunakan pola temuan → alasan teknis → implikasi.

❌ Don't

  • Jangan mengarang angka/hasil/tabel.
  • Jangan menambah komponen arsitektur baru.
  • Jangan memperluas scope fault tolerance.
  • Jangan menambah metrik baru.
