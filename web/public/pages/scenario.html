Chapter 4.1

Test Scenario Setup

Establishing a standardized test scenario as a guideline for experiments comparing the performance of RAFT and SmartBFT consensus algorithms on Hyperledger Fabric network.

Important: Stage 4.1 does not produce performance metrics (TPS/latency/CPU). This stage produces scenario artifacts that will be used in stages 4.2–4.6. Performance values will appear after execution (4.4) and analysis (4.5–4.6).

A

Stage 4.1 Objectives

This stage establishes a standardized test scenario to ensure:

  • Fair Comparison — Both networks receive equivalent testing treatment, so performance differences can be attributed directly to consensus mechanism characteristics
  • Repeatability — Testing procedures can be repeated with the same parameters, not due to workload or procedural differences
4.1.1

Stage 4.1 Output (Structured Deliverables)

Stage 4.1 produces a final test scenario document that serves as reference for running experiments in stages 4.2–4.4. The following outputs are mandatory:

  • Test Scenario Parameters (final) — Transaction count, submission pattern, concurrency, iterations, success criteria
  • Fairness Controls — List of controls ensuring fair RAFT vs SmartBFT comparison
  • Dummy Transaction Definition — Transaction source, payload consistency, success criteria
  • Test Execution SOP — Standard operating procedure from network start to completion
  • Data Capture Plan — Raw data types that must be recorded for metric calculation
  • Metric Mapping — Operational definitions showing how metrics are calculated from raw data

D

Dummy Transaction Definition

Dummy transactions are test transactions sent from the web prototype (client) to load the blockchain network without carrying production/real data. All transactions use the same payload format to ensure consistent workload.

Success Criteria

A transaction is considered successful when:

  • Transaction is processed until committed to the ledger
  • Client receives a success response

Note: Detailed payload structure (fields/attributes) will be documented in section 4.3.

E

Fairness Controls

To ensure fair comparison, the following controls are applied equally to RAFT and SmartBFT:

Same payload structure
Same chaincode
Same channel
Same environment/infrastructure
Same execution parameters
Same recording procedure
F

Test Execution SOP

This SOP defines the testing "rules of engagement" that will be executed in stage 4.4.

1

Start Network A (RAFT)

Launch the RAFT network and verify status is ready to accept transactions

2

Submit Dummy Transactions

Send {JUMLAH_TRANSAKSI} dummy transactions from web prototype using {SEQUENTIAL/PARALLEL} pattern with {CONCURRENCY} concurrency

3

Record Timestamps & Outcome

Log start time, end time, count of successful/failed transactions

4

Capture Resource Metrics

Record CPU & memory monitoring logs during execution

5

Repeat Test

Repeat steps 2–4 for {JUMLAH_PERCOBAAN} iterations

6

Test Network B (SmartBFT)

Execute the same procedure on SmartBFT network with identical parameters

G

Data Capture Plan (Raw Data)

To enable metric calculation in stages 4.5–4.6, stage 4.1 specifies the following minimum raw data:

Transaction Data

  • start_time — Test start timestamp
  • end_time — Test end timestamp
  • tx_submitted — Transactions submitted
  • tx_success — Successful transactions
  • tx_failed — Failed transactions
  • commit_evidence — Commit proof/log

Resource Data

  • cpu_avg — Average CPU usage
  • cpu_peak — Peak CPU usage
  • mem_avg — Average memory usage
  • mem_peak — Peak memory usage

Fault Tolerance Data

  • fault_tolerance_note — Scope note
  • "Analyzed within defined scope; no active failure injection testing"
H

Metric Mapping (Raw Data → Metrics)

Operational definitions for consistent analysis:

Throughput (TPS)

TPS = tx_success / (end_time - start_time)

Transactions per second calculated from successful transactions divided by execution duration

Latency

latency_avg = average(response_times)

Measured from transaction response time. Using average (mean) method consistently

Resource Usage

cpu_usage = cpu_avg | cpu_peak
mem_usage = mem_avg | mem_peak

Based on CPU/memory summary during scenario execution

Fault Tolerance

fault_tolerance = descriptive_analysis(scope)

Presented according to scope: descriptive or based on limited disruption simulation results (if any)
