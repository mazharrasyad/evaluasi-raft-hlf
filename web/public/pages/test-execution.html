Chapter 4.3

Pelaksanaan Pengujian dan Pencatatan Aktivitas Sistem

Tahap ini menjalankan transaksi dummy secara deterministik pada jaringan RAFT dan SmartBFT, mengukur durasi eksekusi end-to-end, dan menjamin setiap transaksi benar-benar committed ke ledger.

Sesuai spesifikasi 4.3: Pengujian dijalankan secara deterministik dengan pencatatan waktu submit dan waktu commit untuk setiap transaksi. Data ini menjadi dasar perhitungan metrik kinerja pada tahap berikutnya.

4.3.1

Konfigurasi Pengujian

Landasan Penetapan Skenario

Pengujian dilakukan dalam dua pola beban, yaitu sequential sebagai baseline untuk mengukur overhead dasar konsensus tanpa pengaruh antrean, serta parallel untuk merepresentasikan kondisi operasional ketika banyak permintaan transaksi masuk secara bersamaan. Tingkat concurrency ditetapkan bertahap (5, 10, 20) dan jumlah transaksi ditetapkan pada nilai representatif (200, 500, 800) agar perbedaan karakteristik koordinasi konsensus Raft dan SmartBFT dapat diamati secara konsisten pada lingkungan pengujian yang sama.

🔵 Sequential (Concurrency=1)

Dipakai sebagai baseline: mengukur overhead konsensus per transaksi tanpa efek antrean/penjadwalan. Setiap transaksi melewati satu siklus konsensus penuh.

🟠 Parallel (Concurrency>1)

Dipakai sebagai kondisi realistis: request banyak masuk bersamaan, muncul efek antrian, batching, dan koordinasi konsensus.

✓ Variabel Terkontrol

Variabel bebas hanya konsensus (Raft vs SmartBFT). Yang lain dikunci: payload dummy (256 bytes), chaincode pelaporan, channel masing-masing network, konfigurasi identik, dan environment yang sama.

A. Baseline — SEQUENTIAL

Pattern: SEQUENTIAL | Concurrency: 1 | Interval: 0 ms | Iterations: 3 per skenario
ID Transactions Tujuan Status
B1 200 Baseline awal & validasi sistem stabil Pending
B2 500 Baseline representatif (titik utama perbandingan) Pending
B3 800 Baseline mendekati batas tanpa paralel Pending

Kenapa 200/500/800? — 200 cukup untuk pemanasan & baseline cepat. 500 jadi titik utama yang stabil untuk perbandingan. 800 menguji scaling tanpa dipengaruhi paralelisme.

B. Realistic Load — PARALLEL

Pattern: PARALLEL | Interval: 0 ms | Iterations: 3 per skenario
ID Transactions Concurrency Tujuan Status
P1 500 5 Load ramai ringan Pending
P2 500 10 Load ramai menengah (utama) Pending
P3 500 20 Load ramai tinggi Pending
P4 800 5 Scaling + paralel Pending
P5 800 10 Scaling utama + paralel Pending
P6 800 20 Batas performa + paralel Pending

Kenapa concurrency 5/10/20? — 5: paralel ringan umum di sistem web. 10: sweet spot untuk beda konsensus mulai kelihatan. 20: tekanan tinggi tapi masih realistis untuk uji VPS.

4.3.4

Struktur Data Hasil Uji

Sesuai spesifikasi skenario 4.1, setiap hasil pengujian dicatat dengan struktur standar berikut:

Field Tipe Deskripsi
consensus string Jenis konsensus (raft | smartbft)
txTotal number Total transaksi yang dieksekusi
txSuccess number Jumlah transaksi sukses (committed)
durationSec number Durasi eksekusi dalam detik
startTimestamp ISO-8601 Waktu mulai pengujian
endTimestamp ISO-8601 Waktu selesai pengujian
latencies[] number[] Array latency per transaksi (ms)
cpuUsage number Penggunaan CPU rata-rata (%)
memoryUsage number Penggunaan memory rata-rata (MB)
4.3.5

Pencatatan Hasil

Hasil pengujian dicatat secara otomatis setelah eksekusi selesai. Data mencakup throughput, latency, dan success rate untuk setiap network.
