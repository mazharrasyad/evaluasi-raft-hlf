Bab 4.6.1

Algoritma Raft

Sub bab ini menjelaskan bagaimana Raft bekerja sebagai mekanisme konsensus CFT pada Hyperledger Fabric v2 dan v3. Fokus pembahasan mencakup alur kerja (leader election, replikasi log, hingga commit) beserta perbandingan singkat dengan opsi SmartBFT sebagai konsensus BFT pada Fabric v3.

Fase Utama dalam Raft

Dalam konteks penelitian ini, alur Raft dipaparkan sebagai rangkaian fase berulang yang menjaga konsistensi log antarnode. Setiap fase menegaskan peran leader sebagai koordinator dan follower sebagai replika.

  1. Leader election: node kandidat meminta suara untuk menjadi leader ketika timeout.
  2. Log replication: leader menerima transaksi, membentuk batch, lalu mengirim AppendEntries.
  3. Commit & apply: mayoritas acknowledgment membuat blok dianggap valid dan diterapkan ke state.
  4. Recovery: node tertinggal mengejar log dari leader hingga konsisten kembali.

Pseudocode Raft (HLF v2 & v3)

Pseudocode berikut merangkum proses yang sama pada Fabric v2 dan v3, dengan penyesuaian parameter konfigurasi seperti ukuran batch, timeout, dan mekanisme pengiriman blok. 

// Leader menerima transaksi
onReceiveTransaction(tx):
    batch.append(tx)
    if batch.size >= batchSize or timeout:
        block = createBlock(batch)
        for follower in followers:
            send AppendEntries(block) to follower
        batch.clear()

// Follower menerima blok
onAppendEntries(block):
    log.append(block)
    send Ack to leader

// Leader menerima ack
onAck(follower):
    ackCount[follower] += 1
    if ackCount quorum:
        commit(block)
        broadcast block to peers

// Election
onTimeout():
    becomeCandidate()
    startElection()

Fabric v2 — Raft Standar

CFT
1. Terima transaksi & masuk batch statis.
⬇
2. Leader membentuk blok saat batch penuh/timeout.
⬇
3. Kirim AppendEntries ke follower.
⬇
4. Follower ack, leader commit saat quorum.
⬇
5. Broadcast blok ke peer & apply state.

Fabric v3 — Raft Standar

Pipeline
1. Tx masuk buffer & scheduler batch dinamis.
⬇
2. Leader memotong blok & menyiapkan metadata ordering.
⬇
3. AppendEntries + pipeline delivery ke follower.
⬇
4. Quorum ack → commit, blok disalurkan ke peer.
⬇
5. Sinkronisasi cepat untuk node yang tertinggal.

Raft Varian (Eksperimen)

Tuning
1. Timeout election dipersingkat untuk respons cepat.
⬇
2. Batch adaptif menyesuaikan beban transaksi.
⬇
3. AppendEntries paralel untuk menekan latensi.
⬇
4. Ack quorum diukur per fase, commit lebih agresif.
⬇
5. Monitoring backlog untuk trigger recovery.

Varian + SmartBFT (Fabric v3)

BFT
1. Leader mengusulkan blok (PrePrepare).
⬇
2. Replika validasi & broadcast Prepare.
⬇
3. Quorum Prepare → kirim Commit.
⬇
4. Quorum Commit → blok final & broadcast ke peer.
⬇
5. Audit tambahan untuk ketahanan byzantine.

Perbandingan Implementasi v2 & v3

  • Fabric v2: fokus pada stabilitas RAFT standar dengan konfigurasi CFT yang teruji.
  • Fabric v3: menawarkan perbaikan pipeline serta opsi konsensus SmartBFT untuk kebutuhan toleransi Byzantine.
  • Varian penelitian: penyesuaian parameter dan skenario beban digunakan untuk melihat efek pada throughput dan latency.

SmartBFT sebagai Pembanding

Pada Fabric v3, SmartBFT menjadi opsi konsensus BFT. Flow mirip Raft, namun menggunakan protokol BFT (Byzantine Fault Tolerance) dengan quorum lebih besar dan validasi tambahan sehingga berdampak pada latensi namun meningkatkan ketahanan terhadap perilaku byzantine. 

// SmartBFT (skema sederhana)
onProposeBlock(block):
    broadcast PrePrepare(block) to all

onPrePrepare(block):
    if valid(block):
        broadcast Prepare(block)

onPrepare(block):
    if receive Prepare from quorum:
        broadcast Commit(block)

onCommit(block):
    if receive Commit from quorum:
        commit(block)
        broadcast block to peers

Ringkasan Sub Bab 4.6.1

  • RAFT diposisikan sebagai mekanisme CFT yang menyeimbangkan konsistensi dan ketersediaan jaringan.
  • Alur leader election dan log replication menjadi kunci perbedaan performa ketika beban transaksi meningkat.
  • SmartBFT diperkenalkan sebagai pembanding ketika dibutuhkan toleransi Byzantine yang lebih tinggi.
