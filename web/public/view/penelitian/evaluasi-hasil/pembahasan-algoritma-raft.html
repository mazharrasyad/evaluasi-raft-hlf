Bab 4.6.2

Pembahasan Algoritma Konsensus RAFT

Subbab ini membahas prinsip kerja algoritma konsensus RAFT pada layanan ordering Hyperledger Fabric (HLF) dan menyajikan pseudocode yang merepresentasikan alur RAFT pada Fabric v2 dan Fabric v3. Selain itu, dibahas perbedaan implementasi RAFT standar dan RAFT varian pada eksperimen ini (terutama pada parameter pembentukan blok), serta posisi SmartBFT sebagai opsi konsensus BFT yang tersedia pada Fabric v3.

Bab 4.6.2.1

Garis Besar Algoritma RAFT pada HLF

RAFT adalah algoritma crash fault tolerant (CFT) berbasis pemimpin (leader-based) yang menjaga konsistensi replika melalui leader election dan log replication. Pada HLF, “log entry” RAFT dapat dipetakan sebagai blok (atau batch transaksi yang akan menjadi blok), yang direplikasi antar orderer (consenter) dan dinyatakan committed ketika memperoleh persetujuan mayoritas (quorum).

Peran Node

  • Follower: menerima heartbeat dan replikasi log dari leader.
  • Candidate: memulai pemilihan saat timeout, meminta suara (RequestVote).
  • Leader: mengoordinasikan pemesanan transaksi, mengirim heartbeat, mereplikasi log.

Konsep Kunci

  • term: penanda era kepemimpinan; meningkat pada proses election.
  • log index: urutan entry; dipakai untuk konsistensi dan commit index.
  • quorum: mayoritas node; syarat commit pada CFT.

Alur Tingkat Tinggi

  1. Leader menerima transaksi, membentuk batch/blok.
  2. Leader mengirim AppendEntries (blok) ke followers.
  3. Mayoritas ack → commit; blok disajikan ke peer (deliver).
Bab 4.6.2.2

Pseudocode RAFT — Fabric v2

Pseudocode berikut merangkum perilaku RAFT pada orderer Fabric v2 untuk dua komponen inti: (1) pemilihan leader dan (2) replikasi log blok. Pada konteks HLF, “entry” merepresentasikan blok yang dibentuk dari transaksi menggunakan parameter batch (BatchTimeout, MaxMessageCount, dan ukuran byte).

Algoritma 4.1 — RAFT (Fabric v2)

Ringkasan pseudocode RAFT dengan fokus pada orderer leader, follower, dan proses commit quorum. 

STATE: role ∈ {Follower, Candidate, Leader}
PERSISTENT: currentTerm, votedFor, log[]
VOLATILE: commitIndex, lastApplied
LEADER ONLY: nextIndex[peer], matchIndex[peer]

onStart():
  role ← Follower
  resetElectionTimer(randomizedTimeout)

onElectionTimeout() when role != Leader:
  role ← Candidate
  currentTerm ← currentTerm + 1
  votedFor ← self
  votes ← 1
  resetElectionTimer(randomizedTimeout)
  broadcast RequestVote(term=currentTerm, lastLogIndex, lastLogTerm)

onReceive(RequestVote(term, candId, lastLogIndex, lastLogTerm)):
  if term > currentTerm: currentTerm ← term; role ← Follower; votedFor ← null
  if term < currentTerm: reply VoteGranted=false
  else if (votedFor is null or votedFor == candId) and logIsUpToDate(lastLogIndex,lastLogTerm):
    votedFor ← candId
    resetElectionTimer(randomizedTimeout)
    reply VoteGranted=true
  else reply VoteGranted=false

onReceive(VoteResponse(term, granted)) when role == Candidate:
  if term > currentTerm: currentTerm ← term; role ← Follower; votedFor ← null; return
  if granted: votes ← votes + 1
  if votes >= majority:
    role ← Leader
    initialize nextIndex[*] ← lastLogIndex+1; matchIndex[*] ← 0
    sendHeartbeat()

sendHeartbeat() when role == Leader:
  periodically every HeartbeatTick:
    broadcast AppendEntries(term=currentTerm, leaderId, prevLogIndex, prevLogTerm, entries=[], leaderCommit=commitIndex)

// Ordering service: menerima transaksi lalu membentuk blok (entry)
onLeaderReceiveTransaction(tx) when role == Leader:
  bufferTx.append(tx)
  if shouldCutBlock(bufferTx, BatchTimeout, MaxMessageCount, PreferredMaxBytes, AbsoluteMaxBytes):
    block ← makeBlock(bufferTx); bufferTx.clear()
    log.append(blockEntry(block))
    broadcast AppendEntries(term=currentTerm, entries=[blockEntry], leaderCommit=commitIndex)

onReceive(AppendEntries(term, leaderId, prevLogIndex, prevLogTerm, entries, leaderCommit)):
  if term < currentTerm: reply Success=false
  if term > currentTerm: currentTerm ← term; role ← Follower; votedFor ← null
  resetElectionTimer(randomizedTimeout)
  if !logMatches(prevLogIndex, prevLogTerm): reply Success=false
  else:
    deleteConflictingEntriesFrom(prevLogIndex+1)
    append(entries)
    if leaderCommit > commitIndex:
      commitIndex ← min(leaderCommit, lastLogIndex)
    reply Success=true, matchIndex=lastLogIndex

onLeaderReceive(AppendResponse(peer, term, success, matchIndex)) when role == Leader:
  if term > currentTerm: currentTerm ← term; role ← Follower; votedFor ← null; return
  if success:
    matchIndex[peer] ← matchIndex
    nextIndex[peer] ← matchIndex + 1
    // commit jika entry direplikasi ke mayoritas
    for N from lastLogIndex downTo commitIndex+1:
      if countPeersWith(matchIndex[*] ≥ N) ≥ majority and log[N].term == currentTerm:
        commitIndex ← N
        broadcast AppendEntries(term=currentTerm, entries=[], leaderCommit=commitIndex)
        break
  else:
    nextIndex[peer] ← max(1, nextIndex[peer]-1)
    retry AppendEntries for peer

applyCommitted():
  while lastApplied < commitIndex:
    lastApplied ← lastApplied + 1
    deliverBlockToLedger(log[lastApplied])

Catatan: fungsi shouldCutBlock() pada HLF dipengaruhi oleh konfigurasi batch. Pada eksperimen ini, konfigurasi batch menjadi pembeda utama antara “RAFT standar” dan “RAFT varian”.

Bab 4.6.2.3

Pseudocode RAFT — Fabric v3

Pada Fabric v3, mekanisme RAFT (etcdraft) tetap mempertahankan prinsip yang sama seperti v2: pemilihan leader, heartbeat, replikasi log, dan commit quorum. Pembaruan utama pada v3 dalam konteks penelitian ini adalah ketersediaan opsi konsensus BFT (SmartBFT) sebagai pembanding.

Algoritma 4.2 — RAFT (Fabric v3)

Pseudocode RAFT v3 menambahkan penekanan pada plugin konsensus (RAFT/BFT) di sisi orderer. 

INPUT: consensusType ∈ {etcdraft, BFT}

if consensusType == etcdraft:
  runRaftLoop()   // sama secara prinsip dengan RAFT v2

function runRaftLoop():
  while running:
    if role == Leader:
      receiveTx()
      maybeCutBlockUsingBatchPolicy()
      replicateBlockWithAppendEntries()
      commitWhenQuorumAcks()
      sendHeartbeats()
    else:
      followLeaderAppendEntries()
      startElectionOnTimeout()

function maybeCutBlockUsingBatchPolicy():
  // Parameter batch berbeda antara konfigurasi standar vs varian
  if shouldCutBlock(bufferTx, BatchTimeout, MaxMessageCount, PreferredMaxBytes, AbsoluteMaxBytes):
    block ← makeBlock(bufferTx)
    log.append(block)

function commitWhenQuorumAcks():
  if replicatedToMajority(blockIndex):
    commitIndex ← blockIndex
    appendToLocalLedger(block)
    serveCommittedBlocksToPeers()

Pada eksperimen ini, mode RAFT v3 tetap menggunakan etcdraft. Untuk pembanding BFT, digunakan plugin BFT (SmartBFT) yang dijelaskan pada Bab 4.6.2.5.

Bab 4.6.2.4

Perbedaan RAFT Standar vs RAFT Varian (Eksperimen)

Perbedaan “standar” dan “varian” pada penelitian ini terutama terletak pada kebijakan pembentukan blok (block cutting) melalui parameter batch di configtx.yaml. Parameter RAFT inti (TickInterval/ElectionTick/HeartbeatTick) tetap sama, sehingga perubahan performa lebih banyak dipengaruhi oleh cara transaksi dikemas menjadi blok serta beban komunikasi replikasi.

Parameter RAFT Standar RAFT Varian Implikasi Utama
BatchTimeout 2s 1s Timeout lebih kecil cenderung menurunkan latensi pada beban rendah, tetapi dapat menambah overhead blok.
MaxMessageCount 10 50 Varian memungkinkan lebih banyak transaksi per blok → potensi throughput naik pada beban tinggi.
AbsoluteMaxBytes 99 MB 20 MB Batas maksimum ukuran blok; memengaruhi risiko blok besar vs stabilitas jaringan.
PreferredMaxBytes 512 KB 4 MB Ukuran target batch; semakin besar dapat mengurangi frekuensi commit namun menambah waktu tunggu pengisian batch.

Interpretasi terhadap Throughput

Dengan MaxMessageCount lebih besar dan PreferredMaxBytes lebih longgar, RAFT varian berpotensi meningkatkan throughput karena lebih banyak transaksi dapat diselesaikan per blok yang direplikasi. Namun, manfaat tersebut paling terasa saat beban transaksi cukup tinggi untuk mengisi batch.

Interpretasi terhadap Latency

BatchTimeout yang lebih kecil (1s) pada varian cenderung memotong blok lebih cepat saat transaksi tidak cukup untuk memenuhi batas jumlah/ukuran, sehingga latency dapat lebih rendah pada beban ringan–sedang. Sebaliknya, blok yang lebih sering terbentuk dapat menambah overhead replikasi dan validasi.

Bab 4.6.2.5

SmartBFT sebagai Pembanding (Fabric v3)

RAFT hanya menjamin konsistensi ketika kegagalan bersifat crash (node berhenti/terputus), sehingga termasuk kategori CFT. Pada Fabric v3, tersedia opsi konsensus SmartBFT (melalui tipe orderer BFT) untuk menghadapi skenario Byzantine faults (node bertindak arbitrer/malicious).

Prinsip Dasar SmartBFT

  • Model BFT: toleran terhadap node yang berperilaku tidak benar.
  • Kebutuhan node: umumnya \(n \ge 3f + 1\) untuk menoleransi \(f\) Byzantine faults.
  • View change: mekanisme pergantian pemimpin ketika pemimpin gagal/bermasalah.

Perbandingan Konseptual RAFT vs SmartBFT

  • Ketahanan: RAFT (CFT) vs SmartBFT (BFT).
  • Overhead: SmartBFT biasanya membutuhkan lebih banyak pesan/quorum certificate → potensi latency lebih tinggi.
  • Konteks penelitian: SmartBFT dipakai sebagai pembanding untuk melihat trade-off performa vs ketahanan.

Dengan demikian, SmartBFT bukan “varian RAFT”, melainkan kelas konsensus berbeda yang memprioritaskan ketahanan terhadap perilaku arbitrer. Dalam evaluasi hasil, interpretasi metrik (throughput/latency/resource) perlu mempertimbangkan bahwa SmartBFT secara alamiah memiliki biaya koordinasi yang lebih tinggi dibanding RAFT, namun menawarkan jaminan keamanan yang lebih kuat.
