Bab 4.1.1

Algoritma Konsensus RAFT

Algoritma konsensus RAFT (Replicated And Fault Tolerant) merupakan algoritma konsensus yang dirancang untuk menjaga konsistensi data pada sistem terdistribusi dengan pendekatan yang sederhana dan mudah dipahami. RAFT bekerja dengan membagi proses konsensus ke dalam beberapa mekanisme utama, yaitu leader election, log replication, dan commitment, sehingga seluruh node dalam jaringan dapat memiliki urutan data yang konsisten. Algoritma ini termasuk ke dalam kategori Crash Fault Tolerant (CFT), yang mampu menangani kegagalan node akibat crash atau ketidakresponsifan, namun tidak dirancang untuk menghadapi perilaku node yang bersifat jahat (Byzantine fault).

Pada RAFT, hanya satu node yang bertindak sebagai leader dalam satu periode (term). Leader bertanggung jawab untuk menerima transaksi dari klien, mengatur urutan transaksi, serta mereplikasi log transaksi ke seluruh node lain yang berperan sebagai follower. Follower tidak memproses transaksi secara langsung, melainkan menunggu instruksi dari leader melalui mekanisme heartbeat. Apabila heartbeat tidak diterima dalam rentang waktu tertentu, maka mekanisme leader election akan dijalankan untuk memilih pemimpin baru. Pendekatan ini memastikan bahwa sistem tetap berjalan meskipun terjadi kegagalan pada salah satu node.

Implementasi RAFT pada Hyperledger Fabric v2

Hyperledger Fabric v2 mengimplementasikan algoritma konsensus RAFT sebagai mekanisme default pada ordering service. Implementasi ini menggunakan tipe konsensus RAFT untuk mengatur urutan transaksi sebelum dibentuk menjadi blok dan didistribusikan ke peer. Dengan tidak menerapkan mekanisme Byzantine Fault Tolerance, Fabric v2 dengan RAFT difokuskan pada efisiensi pemrosesan transaksi, sehingga mampu menghasilkan throughput yang tinggi dan latency yang relatif rendah pada lingkungan jaringan yang bersifat permissioned dan terpercaya.

Dalam Fabric v2, seluruh proses pengurutan transaksi terpusat pada leader orderer. Transaksi yang diterima akan direplikasi ke follower melalui mekanisme log replication hingga mencapai mayoritas (majority). Setelah mayoritas node menyetujui log transaksi tersebut, transaksi dianggap valid untuk dibentuk menjadi blok. Model ini mendukung konsistensi data yang kuat, namun juga menimbulkan potensi bottleneck pada node leader ketika beban transaksi meningkat secara signifikan.

Dari sisi fault tolerance, RAFT pada Fabric v2 mampu menangani kegagalan node dengan cepat melalui deteksi timeout dan pemilihan leader baru. Selama mayoritas node masih aktif, sistem tetap dapat melanjutkan proses konsensus tanpa kehilangan konsistensi data. Karakteristik ini menjadikan Fabric v2 dengan RAFT cocok sebagai baseline evaluasi performa dalam penelitian ini.

Pseudocode Algoritma RAFT pada Fabric v2

// Algoritma RAFT pada Hyperledger Fabric v2
class RaftNode {
    state: enum {FOLLOWER, CANDIDATE, LEADER}
    currentTerm: int
    votedFor: NodeId | null
    log: Array<LogEntry>
    commitIndex: int
    lastApplied: int
    electionTimeout: Timer
    heartbeatInterval: Timer

    onStartup() {
        state = FOLLOWER
        currentTerm = 0
        votedFor = null
        electionTimeout = random(150ms, 300ms)
        startElectionTimer()
    }

    onElectionTimeout() {
        if (state == FOLLOWER) {
            state = CANDIDATE
            currentTerm++
            votedFor = self
            votesReceived = 1
            
            for node in cluster {
                sendRequestVote(node, currentTerm, 
                    log.lastIndex(), 
                    log.lastTerm())
            }
            
            electionTimeout = random(150ms, 300ms)
            startElectionTimer()
        }
    }

    onReceiveVote(candidateTerm, candidateId, 
                     lastLogIndex, lastLogTerm) {
        if (candidateTerm > currentTerm) {
            currentTerm = candidateTerm
            state = FOLLOWER
            votedFor = null
        }
        
        if (candidateTerm == currentTerm && 
            votedFor == null &&
            isLogUpToDate(lastLogIndex, lastLogTerm)) {
            votedFor = candidateId
            resetElectionTimer()
            return true
        }
        return false
    }

    onReceiveHeartbeat(leaderTerm, leaderId, 
                          prevLogIndex, prevLogTerm,
                          entries, leaderCommit) {
        if (leaderTerm >= currentTerm) {
            state = FOLLOWER
            currentTerm = leaderTerm
            resetElectionTimer()
        }
        
        if (leaderTerm == currentTerm && 
            state != FOLLOWER) {
            state = FOLLOWER
        }
        
        if (matchLog(prevLogIndex, prevLogTerm)) {
            appendEntries(entries)
            commitIndex = min(leaderCommit, 
                log.lastIndex())
            return true
        }
        return false
    }

    onBecomeLeader() {
        state = LEADER
        for node in cluster {
            nextIndex[node] = log.lastIndex() + 1
            matchIndex[node] = 0
        }
        sendHeartbeat()
        heartbeatInterval = setInterval(sendHeartbeat, 50ms)
    }

    onReceiveTransaction(tx) {
        if (state == LEADER) {
            logEntry = new LogEntry(currentTerm, tx)
            log.append(logEntry)
            
            for node in cluster {
                replicateLog(node)
            }
        }
    }
}

Implementasi RAFT pada Hyperledger Fabric v3

Hyperledger Fabric v3 tetap mempertahankan algoritma RAFT sebagai salah satu mekanisme konsensus utama, namun dengan sejumlah peningkatan pada sisi stabilitas dan efisiensi internal. Meskipun Fabric v3 memperkenalkan opsi konsensus lain seperti SmartBFT, implementasi RAFT standar tetap tersedia dan relevan untuk skenario yang tidak memerlukan toleransi Byzantine.

Pada Fabric v3, mekanisme RAFT mengalami optimasi pada proses replikasi log dan pengelolaan state, seperti penerapan snapshot dan log compaction untuk mengurangi ukuran log yang harus disinkronkan antar node. Selain itu, proses komunikasi antar node dibuat lebih efisien, termasuk optimasi interval heartbeat dan dukungan replikasi log secara batch. Peningkatan ini bertujuan untuk menjaga stabilitas sistem serta mengurangi beban sumber daya ketika jumlah transaksi dan ukuran ledger semakin besar.

Secara fungsional, prinsip kerja RAFT pada Fabric v3 tetap sama dengan versi sebelumnya, yaitu menggunakan satu leader sebagai koordinator transaksi dan follower sebagai replika data. Namun, dengan adanya optimasi tersebut, Fabric v3 diharapkan mampu memberikan kinerja yang lebih stabil pada beban transaksi menengah hingga tinggi, khususnya dalam hal pemanfaatan sumber daya dan waktu pemulihan ketika terjadi kegagalan node.

Pseudocode Algoritma RAFT pada Fabric v3

// Algoritma RAFT pada Hyperledger Fabric v3 (Enhanced)
class RaftNodeV3 {
    state: enum {FOLLOWER, CANDIDATE, LEADER}
    currentTerm: int
    votedFor: NodeId | null
    log: Array<LogEntry>
    commitIndex: int
    lastApplied: int
    electionTimeout: Timer
    heartbeatInterval: Timer
    snapshotIndex: int  // New in v3
    snapshotTerm: int    // New in v3

    onStartup() {
        state = FOLLOWER
        currentTerm = 0
        votedFor = null
        electionTimeout = random(150ms, 300ms)
        snapshotIndex = 0
        snapshotTerm = 0
        loadSnapshot()  // Enhanced: Load from snapshot
        startElectionTimer()
    }

    onElectionTimeout() {
        if (state == FOLLOWER) {
            state = CANDIDATE
            currentTerm++
            votedFor = self
            votesReceived = 1
            
            // Enhanced: Parallel vote requests
            votePromises = parallelRequestVote(cluster, 
                currentTerm, 
                log.lastIndex(), 
                log.lastTerm(),
                snapshotIndex,  // Include snapshot info
                snapshotTerm)
            
            electionTimeout = random(150ms, 300ms)
            startElectionTimer()
        }
    }

    onReceiveVote(candidateTerm, candidateId, 
                     lastLogIndex, lastLogTerm,
                     candidateSnapshotIndex, candidateSnapshotTerm) {
        if (candidateTerm > currentTerm) {
            currentTerm = candidateTerm
            state = FOLLOWER
            votedFor = null
        }
        
        // Enhanced: Check snapshot consistency
        logUpToDate = isLogUpToDate(lastLogIndex, 
            lastLogTerm, 
            candidateSnapshotIndex, 
            candidateSnapshotTerm)
        
        if (candidateTerm == currentTerm && 
            votedFor == null && logUpToDate) {
            votedFor = candidateId
            resetElectionTimer()
            return true
        }
        return false
    }

    onReceiveHeartbeat(leaderTerm, leaderId, 
                          prevLogIndex, prevLogTerm,
                          entries, leaderCommit,
                          leaderSnapshotIndex) {
        if (leaderTerm >= currentTerm) {
            state = FOLLOWER
            currentTerm = leaderTerm
            resetElectionTimer()
        }
        
        // Enhanced: Handle snapshot installation
        if (leaderSnapshotIndex > snapshotIndex) {
            installSnapshot(leaderSnapshotIndex)
        }
        
        if (matchLog(prevLogIndex, prevLogTerm)) {
            appendEntries(entries)
            commitIndex = min(leaderCommit, 
                log.lastIndex())
            
            // Enhanced: Auto-compaction via snapshot
            if (log.size() > snapshotThreshold) {
                createSnapshot()
            }
            
            return true
        }
        return false
    }

    onBecomeLeader() {
        state = LEADER
        for node in cluster {
            nextIndex[node] = log.lastIndex() + 1
            matchIndex[node] = 0
        }
        sendHeartbeat()
        // Enhanced: Optimized heartbeat interval
        heartbeatInterval = setInterval(sendHeartbeat, 40ms)
    }

    onReceiveTransaction(tx) {
        if (state == LEADER) {
            logEntry = new LogEntry(currentTerm, tx)
            log.append(logEntry)
            
            // Enhanced: Batch replication for better throughput
            batchSize = calculateOptimalBatchSize()
            for node in cluster {
                replicateLogBatch(node, batchSize)
            }
        }
    }

    createSnapshot() {
        // Enhanced: Create snapshot for log compaction
        snapshot = captureState(commitIndex)
        snapshotIndex = commitIndex
        snapshotTerm = log[commitIndex].term
        saveSnapshot(snapshot)
        compactLog(snapshotIndex)
    }
}

Relevansi RAFT terhadap Pengujian Kinerja

Dalam konteks penelitian ini, algoritma RAFT digunakan sebagai objek utama evaluasi kinerja konsensus pada Hyperledger Fabric. Implementasi RAFT pada Fabric v2 merepresentasikan kondisi stabil dan umum digunakan, sedangkan implementasi RAFT pada Fabric v3 merepresentasikan versi pengembangan dengan optimasi tambahan. Perbandingan kedua versi ini memungkinkan analisis empiris terhadap pengaruh peningkatan implementasi RAFT terhadap throughput, latency, resource usage, dan fault tolerance dalam skenario simulasi pelaporan maladministrasi.

Dengan demikian, pembahasan RAFT pada subbab ini menjadi landasan konseptual dan operasional untuk analisis hasil pengujian pada subbab-subsekuen, tanpa memasuki ranah Byzantine Fault Tolerance yang secara khusus akan dibahas pada subbab selanjutnya.
