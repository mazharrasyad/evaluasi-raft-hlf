Algoritma RAFT

RAFT adalah algoritma konsensus Crash Fault Tolerant (CFT) yang menjaga konsistensi log pada sistem terdistribusi dengan cara memilih satu leader untuk mengoordinasikan replikasi log ke follower. RAFT memecah persoalan konsensus menjadi tiga mekanisme inti: leader election, log replication, dan safety (aturan komit dan konsistensi).

Peran node

  • Follower: menerima heartbeat & replikasi log
  • Candidate: meminta suara saat timeout
  • Leader: menerima perintah, replikasi, commit

Struktur log

  • term: versi epoch kepemimpinan
  • index: posisi entri pada log
  • commitIndex: batas entri yang “final”

Jaminan

  • majority quorum mencegah split-brain
  • leader hanya commit jika mayoritas mereplikasi
  • log konsisten melalui pemeriksaan prevLogIndex/prevLogTerm

1) Penjelasan / Rumus Inti RAFT

RAFT menggunakan aturan mayoritas untuk election dan commit. Notasi yang umum dipakai:

Quorum mayoritas

Untuk N node orderer, ukuran quorum mayoritas:

Q = ⌊N/2⌋ + 1

RAFT (CFT) dapat tetap berjalan jika jumlah crash/fail-stop yang ditoleransi f memenuhi:

N ≥ 2f + 1

Timeout & heartbeat

Untuk mengurangi risiko pemilihan serentak (split vote), follower memakai election timeout acak. Secara konseptual:

Telection ∈ [Tmin, Tmax] (acak)

Jika follower tidak menerima heartbeat sampai timeout, ia naik term dan menjadi candidate. Pada implementasi orderer RAFT (etcd/raft), parameter ini biasa muncul sebagai TickInterval, ElectionTick, dan HeartbeatTick.

Aturan commit (replikasi log)

Leader menganggap sebuah entri log committed jika entri tersebut sudah tersimpan pada dirinya dan sudah direplikasi ke mayoritas follower. Secara ringkas:

commitIndex = max { i | jumlah(matchIndex ≥ i) ≥ Q }

Untuk menjaga safety, RAFT juga memakai pemeriksaan konsistensi log saat AppendEntries: follower hanya menerima entri baru jika pasangan (prevLogIndex, prevLogTerm) cocok. Jika tidak cocok, follower menolak dan leader akan mengirim ulang entri dari titik yang sesuai.

2) Pseudocode RAFT + Penjelasan

Pseudocode berikut merangkum perilaku inti RAFT (leader election + log replication) dalam bentuk yang disederhanakan. Fokusnya adalah alur keputusan, bukan detail implementasi jaringan. 

// State lokal
state ∈ {FOLLOWER, CANDIDATE, LEADER}
currentTerm ← 0
votedFor ← null
log[] ← []                // setiap entry: (term, command)
commitIndex ← 0
lastApplied ← 0

onTimeout():
  if state != LEADER:
    state ← CANDIDATE
    currentTerm ← currentTerm + 1
    votedFor ← self
    votes ← 1
    send RequestVote(currentTerm, lastLogIndex, lastLogTerm) to all

onReceive(RequestVote(term, lastIdx, lastTerm) from c):
  if term > currentTerm:
    currentTerm ← term
    state ← FOLLOWER
    votedFor ← null

  if term == currentTerm and votedFor in {null, c} and candidateLogIsUpToDate(lastIdx, lastTerm):
    votedFor ← c
    reply VoteGranted
  else:
    reply VoteDenied

onReceive(VoteGranted):
  if state == CANDIDATE:
    votes ← votes + 1
    if votes ≥ Q:
      state ← LEADER
      init nextIndex[follower] ← lastLogIndex + 1
      periodically send AppendEntries(heartbeat or entries)

onClientCommand(cmd):
  if state != LEADER:
    redirect to leader
  else:
    append (currentTerm, cmd) to log
    send AppendEntries(prevLogIndex, prevLogTerm, entries, leaderCommit=commitIndex)

onReceive(AppendEntries(term, prevIdx, prevTerm, entries, leaderCommit) from leader):
  if term < currentTerm:
    reply Fail
  else:
    currentTerm ← term
    state ← FOLLOWER
    reset election timeout

    if log[prevIdx].term != prevTerm:
      reply Fail
    else:
      delete conflicting entries after prevIdx
      append new entries
      commitIndex ← min(leaderCommit, lastLogIndex)
      reply Success

onReceive(AppendEntriesSuccess from follower f):
  update matchIndex[f]
  commitIndex ← max i such that count(matchIndex ≥ i) ≥ Q

Penjelasan pseudocode

  • onTimeout(): follower menjadi candidate, menaikkan term, memberi suara untuk diri sendiri, lalu meminta suara ke node lain.
  • RequestVote: follower memberi suara maksimal 1 kali per term, dan hanya jika log kandidat “cukup mutakhir” (mencegah leader dengan log tertinggal).
  • menjadi leader: jika suara mencapai quorum mayoritas, kandidat menjadi leader dan mulai mengirim heartbeat/AppendEntries secara periodik.
  • onClientCommand: hanya leader yang menerima perintah (transaksi), menambahkannya ke log, lalu mereplikasi ke follower.
  • AppendEntries: follower menolak jika term lebih kecil, atau jika pasangan prevIdx/prevTerm tidak cocok; ini memastikan log tetap konsisten.
  • commitIndex: leader menaikkan commitIndex setelah mayoritas follower mengonfirmasi replikasi, lalu follower mengikuti nilai leaderCommit.

Penjelasan diagram

  1. Follower menunggu heartbeat dari leader aktif.
  2. Jika heartbeat tidak datang sampai timeout, follower menjadi candidate dan mengirim RequestVote.
  3. Jika candidate mendapat quorum mayoritas, ia menjadi leader.
  4. Leader mengirim AppendEntries (heartbeat atau entri log) ke follower; follower mengecek prevLogIndex/prevLogTerm untuk menjaga konsistensi.
  5. Jika mayoritas follower mengakui replikasi entri, leader menaikkan commitIndex. Pada konteks orderer, entri yang sudah committed akan dipaketkan menjadi blok dan didistribusikan ke peer.

4) RAFT pada Hyperledger Fabric v2 dan v3 (selaras dengan konfigurasi lingkungan uji)

Di Hyperledger Fabric, RAFT digunakan pada ordering service dengan tipe etcdraft. Pada penelitian ini, konfigurasi RAFT tidak hanya ditentukan oleh mekanisme election/replication, tetapi juga oleh parameter pembentukan blok (batch) dan jumlah orderer yang digunakan pada skenario standar vs varian (Fabric v2 dan v3).

Pengaruh konfigurasi terhadap kinerja (mengapa konfigurasi berpengaruh)

  • BatchTimeout: batas waktu maksimum sebelum orderer membentuk blok baru. Nilai lebih kecil cenderung menurunkan latency, namun meningkatkan frekuensi proses ordering.
  • MaxMessageCount: jumlah transaksi per blok. Nilai lebih besar dapat menaikkan throughput, tetapi dapat menambah waktu tunggu sampai blok “penuh”.
  • AbsoluteMaxBytes / PreferredMaxBytes: batas ukuran batch/blok. Pengaturan ini memengaruhi efisiensi transmisi dan risiko penumpukan data saat replikasi antar orderer.
  • Jumlah orderer: memengaruhi quorum \(Q\) dan toleransi gangguan \(N \ge 2f+1\). Lebih banyak orderer meningkatkan ketahanan, tetapi menambah overhead replikasi dan komunikasi.
