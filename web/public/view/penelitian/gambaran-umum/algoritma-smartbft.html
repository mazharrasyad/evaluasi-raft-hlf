Algoritma SmartBFT

SmartBFT adalah algoritma konsensus Byzantine Fault Tolerant (BFT) yang dirancang untuk sistem permissioned. Berbeda dengan RAFT (CFT) yang hanya menoleransi crash/fail-stop, SmartBFT menoleransi perilaku byzantine (misal: node jahat, pesan yang dimanipulasi, atau node yang mengirim informasi saling bertentangan). Secara umum, SmartBFT mencapai kesepakatan melalui beberapa fase komunikasi (proposal/prepare/commit) dan mekanisme view change ketika leader dicurigai gagal atau berperilaku tidak benar.

Model gangguan

  • CFT: crash saja (RAFT)
  • BFT: crash + byzantine (SmartBFT)

Fase konsensus

  • Propose: leader mengusulkan batch
  • Prepare: validasi & voting
  • Commit: finalisasi keputusan

Kunci safety

  • quorum BFT 2f+1
  • ukuran cluster minimal 3f+1
  • view change bila leader bermasalah

1) Penjelasan / Rumus Inti SmartBFT

SmartBFT mengacu pada prinsip BFT klasik: jika jumlah node total N, maka sistem dapat menoleransi hingga f node byzantine dengan syarat berikut.

Batas toleransi byzantine

N ≥ 3f + 1

Artinya, untuk menoleransi f = 1 node byzantine, minimal dibutuhkan N = 4 node orderer. Ini sejalan dengan konfigurasi BFT yang umum (empat orderer) pada contoh jaringan.

Quorum keputusan

Keputusan dianggap aman jika didukung oleh quorum BFT:

QBFT = 2f + 1

Dengan quorum 2f+1, dua quorum valid akan selalu beririsan pada minimal f+1 node jujur, sehingga mencegah dua keputusan berbeda (safety).

View / view change

SmartBFT biasanya memiliki konsep view (putaran kepemimpinan). Jika leader tidak mengirim proposal atau terdeteksi bermasalah, replica akan memicu view change untuk memilih leader baru dan melanjutkan konsensus tanpa kehilangan safety.

2) Pseudocode SmartBFT + Penjelasan

Pseudocode berikut memodelkan alur BFT yang disederhanakan: leader mengusulkan batch transaksi, replica melakukan prepare, lalu commit setelah quorum. Istilah dan struktur pesan dibuat ringkas agar mudah dipahami. 

// Parameter
N = jumlah replica
f = ⌊(N-1)/3⌋
Qbft = 2f + 1

// State per replica
view ← 0
seq ← 0

onClientRequest(req):
  send req to leader(view)

leader(view) onReceive(req):
  batch ← collectRequestsUntil(batchMaxCount or batchMaxInterval)
  seq ← seq + 1
  proposal ← (view, seq, hash(batch), batch)
  broadcast PROPOSE(proposal)

replica onReceive(PROPOSE(view, seq, h, batch)):
  if valid(view, seq, batch) and leader(view) is correct sender:
    broadcast PREPARE(view, seq, h, sig(self, view||seq||h))

replica onReceive(PREPARE(view, seq, h, sig_i)):
  store prepareSig(sig_i)
  if countDistinctPrepareSigs(view, seq, h) ≥ Qbft:
    broadcast COMMIT(view, seq, h, sig(self, view||seq||h))

replica onReceive(COMMIT(view, seq, h, sig_i)):
  store commitSig(sig_i)
  if countDistinctCommitSigs(view, seq, h) ≥ Qbft:
    decide(batch)
    append block to ledger

onTimeoutOrLeaderSuspected():
  broadcast VIEW_CHANGE(view+1, evidence)
  if receive Qbft view-change messages:
    view ← view + 1
    newLeader(view) starts proposing

Penjelasan pseudocode

  • Propose: leader membentuk batch transaksi (berdasarkan batas jumlah/waktu) lalu mengirim proposal ke semua replica.
  • Prepare: replica memverifikasi proposal (format, urutan, autentikasi) lalu mengirim tanda tangan/vote ke semua.
  • Commit: setelah menerima 2f+1 prepare yang cocok, replica menyiarkan commit; ketika 2f+1 commit terkumpul, keputusan final dibuat.
  • View change: jika leader macet/bermasalah, replica memulai view change; setelah quorum tercapai, leader baru mengambil alih.

3) Flowchart / Diagram Alur SmartBFT + Penjelasan

Diagram berikut menampilkan alur utama SmartBFT: proposal → prepare → commit → finalisasi blok, serta jalur view change bila leader bermasalah.

Penjelasan diagram

  1. Leader membentuk batch transaksi lalu menyiarkan PROPOSE.
  2. Replica memvalidasi proposal dan menyiarkan PREPARE (bukti dukungan terhadap hash batch).
  3. Jika quorum 2f+1 PREPARE terkumpul, replica masuk fase COMMIT.
  4. Jika quorum 2f+1 COMMIT terkumpul, keputusan final dibuat dan blok dapat ditulis (append) ke ledger.
  5. Jika quorum tidak tercapai atau terjadi timeout, replica menjalankan view change untuk mengganti leader.

4) SmartBFT pada Hyperledger Fabric v2 dan v3 (selaras dengan konfigurasi lingkungan uji)

Pada repo ini, SmartBFT diposisikan sebagai opsi konsensus pada ordering service dengan OrdererType: BFT. Sejalan dengan Bab 4.3, skenario SmartBFT digunakan sebagai pembanding terutama pada lingkungan Fabric v3 varian, sedangkan artefak BFT pada Fabric v2 tersedia sebagai konfigurasi pendamping/rujukan.

Keterkaitan konfigurasi “batch” SmartBFT dengan performa

SmartBFT juga mengelola batch transaksi, namun melalui parameter khusus, misalnya: RequestBatchMaxCount (jumlah request per batch) dan RequestBatchMaxInterval (batas waktu pembentukan batch). Secara konsep, pengaruhnya mirip dengan MaxMessageCount dan BatchTimeout pada RAFT: ada trade-off throughput vs latency, ditambah overhead pesan BFT (prepare/commit) pada tiap batch.

Fabric v2 — artefak BFT (rujukan konfigurasi)

  • Profile BFT: mendefinisikan OrdererType: BFT untuk pembuatan artefak channel.
  • ConsenterMapping: memetakan ID, endpoint, MSPID, serta sertifikat TLS setiap orderer BFT.
  • SmartBFT parameters: contoh parameter batch & view-change (mis. RequestBatchMaxCount, RequestBatchMaxInterval, ViewChangeTimeout).

Contoh file di repo: `fabric-2/raft-standard/network/bft-config/configtx.yaml` dan `fabric-2/raft-variant/network/bft-config/configtx.yaml`.

Fabric v3 varian — skenario pembanding SmartBFT

  • BFT config di network: folder network/bft-config menyediakan profile ChannelUsingBFT dan ConsenterMapping (sejalan Bab 4.3).
  • Opsi SmartBFT di config: terdapat definisi profile SmartBFT pada config/configtx.yaml (mis. profile SmartBFT dengan OrdererType: BFT dan blok SmartBFT).
  • Implikasi eksperimen: karena kebutuhan \(N \ge 3f+1\) dan quorum \(2f+1\), SmartBFT membutuhkan cluster lebih besar dan pertukaran pesan lebih banyak dibanding RAFT; ini biasanya meningkatkan overhead namun menambah ketahanan terhadap byzantine.

Contoh file di repo: `fabric-3/raft-variant/network/bft-config/configtx.yaml` dan `fabric-3/raft-variant/config/configtx.yaml`.
