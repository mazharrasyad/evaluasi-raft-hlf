Algoritma Konsensus RAFT dengan SmartBFT

SmartBFT (Smart Byzantine Fault Tolerance) merupakan mekanisme konsensus yang dirancang untuk meningkatkan ketahanan sistem blockchain terhadap Byzantine faults, yaitu kondisi ketika satu atau lebih node berperilaku tidak jujur, mengirimkan data yang salah, atau bertindak tidak konsisten dengan protokol. Berbeda dengan RAFT yang termasuk ke dalam kategori Crash Fault Tolerant (CFT), SmartBFT memungkinkan sistem tetap mencapai konsensus meskipun terdapat node yang gagal atau berperilaku jahat hingga batas tertentu.

Integrasi SmartBFT dengan RAFT bertujuan untuk mengombinasikan efisiensi koordinasi RAFT dengan ketahanan Byzantine Fault Tolerance. Dalam pendekatan ini, RAFT tetap digunakan sebagai mekanisme dasar untuk pengelolaan kepemimpinan (leader election) dan pengurutan transaksi, sementara SmartBFT berperan sebagai lapisan tambahan yang memperkuat proses validasi dan finalitas transaksi melalui mekanisme kesepakatan kolektif berbasis quorum. Dengan demikian, transaksi tidak hanya diurutkan oleh leader, tetapi juga harus memperoleh persetujuan dari sejumlah node sesuai dengan ambang batas konsensus BFT.

RAFT dengan SmartBFT pada Hyperledger Fabric v2

Pada Hyperledger Fabric v2, SmartBFT belum didukung secara native sebagai mekanisme konsensus. Fabric v2 secara desain difokuskan pada model CFT dengan RAFT sebagai konsensus utama pada ordering service. Oleh karena itu, penerapan RAFT dengan SmartBFT pada Fabric v2 bersifat terbatas dan lebih bersifat konseptual atau eksperimental, bukan bagian dari implementasi resmi yang stabil.

Dalam konteks arsitektur, Fabric v2 tidak menyediakan integrasi langsung antara RAFT dan mekanisme Byzantine Fault Tolerance. Apabila konsep SmartBFT diterapkan secara konseptual pada Fabric v2, maka RAFT tetap berfungsi sebagai pengendali utama alur transaksi, sedangkan mekanisme BFT hanya dapat diposisikan sebagai lapisan verifikasi tambahan di luar konsensus inti. Pendekatan ini menambah kompleksitas komunikasi antar node serta meningkatkan beban komputasi, sehingga berpotensi memengaruhi latency dan pemanfaatan sumber daya.

Oleh karena itu, dalam penelitian ini, Fabric v2 dengan RAFT diperlakukan sebagai baseline CFT, tanpa penerapan SmartBFT secara penuh. Pembahasan RAFT dengan SmartBFT pada Fabric v2 lebih digunakan sebagai referensi konseptual untuk memahami keterbatasan RAFT standar dalam menghadapi Byzantine faults, serta sebagai pembanding terhadap implementasi SmartBFT yang telah terintegrasi secara native pada Fabric v3.

Pseudocode Hybrid RAFT-SmartBFT pada Fabric v2

Pseudocode berikut merupakan representasi konseptual dari integrasi RAFT-SmartBFT yang tidak diimplementasikan secara native pada Fabric v2. Digunakan sebagai referensi untuk memahami keterbatasan RAFT standar. 

// Hybrid RAFT-SmartBFT pada Hyperledger Fabric v2 (Experimental)
class RaftSmartBFTNode {
    state: enum {FOLLOWER, CANDIDATE, LEADER}
    currentTerm: int
    log: Array<LogEntry>
    bftState: BFTState  // SmartBFT state
    signatures: Map<NodeId, Signature>  // BFT signatures
    quorumSize: int  // (N + f) / 2 where f = faulty nodes

    onStartup() {
        state = FOLLOWER
        currentTerm = 0
        bftState = new BFTState()
        quorumSize = calculateQuorum(cluster.size())
        startElectionTimer()
    }

    onElectionTimeout() {
        // RAFT leader election
        if (state == FOLLOWER) {
            state = CANDIDATE
            currentTerm++
            votedFor = self
            votesReceived = 1
            
            for node in cluster {
                sendRequestVote(node, currentTerm, 
                    log.lastIndex(), 
                    log.lastTerm())
            }
            
            electionTimeout = random(150ms, 300ms)
            startElectionTimer()
        }
    }

    onReceiveTransaction(tx) {
        if (state == LEADER) {
            // Step 1: RAFT log replication
            logEntry = new LogEntry(currentTerm, tx)
            log.append(logEntry)
            
            for node in cluster {
                replicateLog(node)
            }
            
            // Step 2: SmartBFT validation phase
            proposal = createProposal(logEntry)
            signature = sign(proposal, privateKey)
            signatures[self] = signature
            
            for node in cluster {
                sendProposal(node, proposal, signature)
            }
        }
    }

    onReceiveProposal(proposerId, proposal, signature) {
        // SmartBFT: Validate proposal
        if (verifySignature(proposal, signature, proposerId)) {
            if (validateProposal(proposal)) {
                signatures[proposerId] = signature
                
                // Check if quorum reached
                if (signatures.size() >= quorumSize) {
                    // Commit transaction with BFT guarantee
                    commitTransaction(proposal.tx, signatures)
                }
            }
        }
    }

    onReceiveLogReplication(leaderTerm, entries) {
        // RAFT: Standard log replication
        if (leaderTerm >= currentTerm) {
            state = FOLLOWER
            currentTerm = leaderTerm
            resetElectionTimer()
        }
        
        if (matchLog(prevLogIndex, prevLogTerm)) {
            appendEntries(entries)
            
            // Trigger BFT validation for each entry
            for entry in entries {
                initiateBFTValidation(entry)
            }
        }
    }

    commitTransaction(tx, signatures) {
        // SmartBFT: Commit with quorum signatures
        commitProof = createCommitProof(tx, signatures)
        commitIndex++
        log[commitIndex].committed = true
        log[commitIndex].bftProof = commitProof
        
        // Apply to state machine
        applyToStateMachine(tx)
    }
}

  1. RAFT Leader Election: Proses pemilihan leader menggunakan mekanisme RAFT standar. Candidate mengirim RequestVote dan memperoleh suara mayoritas untuk menjadi leader.
  2. RAFT Log Replication: Leader menerima transaksi dan mereplikasikannya ke follower melalui mekanisme AppendEntries standar RAFT. Transaksi ditambahkan ke log setiap node.
  3. SmartBFT Proposal Phase: Setelah log replication selesai, leader membuat proposal untuk transaksi tersebut dan mengirimkannya ke semua node untuk validasi SmartBFT. Setiap node memverifikasi proposal dan menandatanganinya jika valid.
  4. SmartBFT Validation: Node-node melakukan validasi proposal secara independen. Validasi meliputi verifikasi tanda tangan, konsistensi data, dan aturan bisnis. Setiap node yang menyetujui mengirim signature kembali ke leader.
  5. Quorum Collection: Leader mengumpulkan signature dari node-node yang menyetujui proposal. Sistem menunggu hingga mencapai quorum (mayoritas node) sebelum menganggap transaksi valid.
  6. Commit dengan BFT Guarantee: Setelah quorum tercapai, transaksi di-commit dengan jaminan Byzantine Fault Tolerance. Transaksi ini sekarang memiliki finalitas yang kuat dan tahan terhadap perilaku node yang jahat.
  7. Overhead Kompleksitas: Pendekatan hybrid ini menambah overhead komunikasi dan komputasi karena memerlukan dua fase konsensus (RAFT + SmartBFT), sehingga berpotensi meningkatkan latency dibandingkan RAFT standar.

RAFT dengan SmartBFT pada Hyperledger Fabric v3

Hyperledger Fabric v3 memperkenalkan dukungan SmartBFT secara native sebagai salah satu opsi mekanisme konsensus pada ordering service. Implementasi ini dirancang secara lebih matang dan terintegrasi, sehingga SmartBFT tidak hanya berfungsi sebagai lapisan tambahan, tetapi menjadi bagian dari proses konsensus yang utuh. Dalam konfigurasi ini, RAFT digunakan untuk menjaga struktur koordinasi dan efisiensi pengurutan transaksi, sementara SmartBFT memastikan bahwa setiap transaksi yang dikomit telah melewati proses validasi kolektif berbasis quorum.

Pada Fabric v3, SmartBFT menerapkan mekanisme pertukaran pesan dan verifikasi tanda tangan antar node untuk mencapai kesepakatan sebelum transaksi dianggap final. Pendekatan ini meningkatkan fault tolerance sistem secara signifikan, karena jaringan tetap dapat beroperasi dengan konsisten meskipun terdapat node yang gagal atau bersikap tidak jujur. Selain itu, Fabric v3 juga mengoptimalkan proses SmartBFT melalui dukungan batch processing, replikasi paralel, serta pengelolaan state yang lebih efisien, sehingga overhead yang ditimbulkan oleh mekanisme BFT dapat ditekan.

Konsekuensi dari penerapan SmartBFT adalah meningkatnya kompleksitas konsensus dibandingkan RAFT standar. Proses validasi tambahan dan komunikasi antar node berpotensi meningkatkan latency dan konsumsi sumber daya, terutama pada skenario beban transaksi tinggi. Namun, trade-off ini sejalan dengan tujuan utama SmartBFT, yaitu meningkatkan keandalan dan keamanan konsensus dalam lingkungan yang membutuhkan tingkat kepercayaan lebih tinggi.

Pseudocode RAFT-SmartBFT pada Fabric v3

Pseudocode berikut merepresentasikan logika algoritma RAFT-SmartBFT yang diimplementasikan secara native dalam binary orderer Hyperledger Fabric v3 dengan dukungan batch processing dan optimasi paralel. 

// RAFT-SmartBFT pada Hyperledger Fabric v3 (Native Support)
class RaftSmartBFTNodeV3 {
    state: enum {FOLLOWER, CANDIDATE, LEADER}
    currentTerm: int
    log: Array<LogEntry>
    bftState: SmartBFTState
    signatures: Map<NodeId, Signature>
    quorumSize: int
    batchQueue: Queue<Transaction>  // Enhanced: Batch processing
    snapshotIndex: int

    onStartup() {
        state = FOLLOWER
        currentTerm = 0
        bftState = new SmartBFTState()
        quorumSize = calculateQuorum(cluster.size())
        batchQueue = new Queue<Transaction>()
        snapshotIndex = 0
        loadSnapshot()
        startElectionTimer()
        startBatchProcessor()  // Enhanced: Auto batch processing
    }

    onReceiveTransaction(tx) {
        if (state == LEADER) {
            // Enhanced: Add to batch queue
            batchQueue.enqueue(tx)
            
            // Process batch when threshold reached
            if (batchQueue.size() >= batchThreshold) {
                batch = batchQueue.dequeueAll()
                processBatch(batch)
            }
        }
    }

    processBatch(batch) {
        // Step 1: RAFT log replication (batch mode)
        logEntry = new LogEntry(currentTerm, batch)
        log.append(logEntry)
        
        // Enhanced: Parallel batch replication
        replicationPromises = parallelReplicateLog(cluster, logEntry)
        
        // Step 2: SmartBFT validation (batch mode)
        proposal = createBatchProposal(logEntry)
        signature = sign(proposal, privateKey)
        signatures[self] = signature
        
        // Enhanced: Parallel proposal distribution
        proposalPromises = parallelSendProposal(cluster, 
            proposal, signature)
        
        await replicationPromises
        await proposalPromises
    }

    onReceiveProposal(proposerId, proposal, signature) {
        // Enhanced: Optimized signature verification
        if (verifySignatureFast(proposal, signature, proposerId)) {
            if (validateBatchProposal(proposal)) {
                signatures[proposerId] = signature
                
                // Enhanced: Optimized quorum check
                if (signatures.size() >= quorumSize) {
                    commitBatch(proposal.batch, signatures)
                }
            }
        }
    }

    commitBatch(batch, signatures) {
        // Enhanced: Batch commit with BFT proof
        commitProof = createBatchCommitProof(batch, signatures)
        commitIndex++
        log[commitIndex].committed = true
        log[commitIndex].bftProof = commitProof
        
        // Enhanced: Parallel state machine application
        parallelApplyToStateMachine(batch)
        
        // Enhanced: Auto snapshot creation
        if (log.size() > snapshotThreshold) {
            createSnapshot()
        }
    }

    onBecomeLeader() {
        state = LEADER
        for node in cluster {
            nextIndex[node] = log.lastIndex() + 1
            matchIndex[node] = 0
        }
        sendHeartbeat()
        // Enhanced: Optimized heartbeat with BFT status
        heartbeatInterval = setInterval(sendHeartbeatWithBFT, 40ms)
    }

    createSnapshot() {
        // Enhanced: Snapshot with BFT state
        snapshot = captureState(commitIndex)
        snapshot.bftState = bftState.snapshot()
        snapshotIndex = commitIndex
        saveSnapshot(snapshot)
        compactLog(snapshotIndex)
    }
}

Penjelasan Diagram:

  1. Batch Queue: Transaksi yang masuk dikumpulkan dalam batch queue hingga mencapai threshold tertentu (jumlah atau waktu). Pendekatan batch meningkatkan efisiensi dengan mengurangi overhead komunikasi.
  2. RAFT Leader Election: Proses pemilihan leader menggunakan mekanisme RAFT yang dioptimasi. Leader terpilih bertanggung jawab untuk mengkoordinasikan batch transaksi.
  3. RAFT Batch Log Replication: Leader mengambil batch dari queue dan mereplikasikannya ke semua follower secara paralel. Replikasi batch lebih efisien dibandingkan replikasi transaksi satu per satu.
  4. SmartBFT Batch Proposal: Setelah batch direplikasi, leader membuat proposal SmartBFT untuk seluruh batch. Proposal ini mencakup hash batch dan metadata yang diperlukan untuk validasi.
  5. Parallel SmartBFT Validation: Semua node melakukan validasi proposal secara paralel. Setiap node memverifikasi tanda tangan, konsistensi batch, dan aturan bisnis secara independen. Validasi paralel mengurangi waktu total validasi.
  6. Quorum Signature Collection: Leader mengumpulkan signature dari node-node yang menyetujui proposal. Sistem menggunakan mekanisme quorum untuk memastikan mayoritas node setuju sebelum commit.
  7. Batch Commit dengan BFT: Setelah quorum tercapai, seluruh batch di-commit dengan jaminan Byzantine Fault Tolerance. Semua transaksi dalam batch memiliki finalitas yang kuat.
  8. Snapshot Creation: Sistem secara berkala membuat snapshot dari state saat ini untuk log compaction. Snapshot ini mengurangi ukuran log dan mempercepat recovery setelah kegagalan node.
  9. Optimasi Native: Implementasi native di Fabric v3 mengoptimalkan komunikasi antara fase RAFT dan SmartBFT, mengurangi overhead dibandingkan pendekatan hybrid konseptual pada Fabric v2.

Rasionalisasi Perbedaan Konfigurasi dengan SmartBFT:

  • RAFT Standar: Menggunakan CFT dengan parameter konservatif untuk kestabilan dan latensi yang dapat diprediksi. Tidak memiliki perlindungan terhadap Byzantine faults.
  • RAFT Variant dengan SmartBFT: Menggunakan BFT dengan parameter agresif untuk throughput tinggi. SmartBFT menambahkan lapisan validasi kolektif yang memerlukan quorum signatures, meningkatkan overhead komunikasi namun memberikan jaminan finalitas yang kuat.
  • Trade-off: Penambahan SmartBFT meningkatkan kompleksitas konsensus dan potensi latency karena memerlukan validasi tambahan dan pertukaran pesan antar node. Namun, hal ini sejalan dengan tujuan meningkatkan keandalan dan keamanan konsensus dalam lingkungan yang membutuhkan tingkat kepercayaan lebih tinggi.
  • Kombinasi: Perbandingan kedua konfigurasi memberikan gambaran menyeluruh tentang bagaimana penambahan mekanisme SmartBFT memengaruhi keseimbangan antara throughput, latency, resource usage, dan fault tolerance dalam simulasi pelaporan maladministrasi.

Relevansi RAFT dengan SmartBFT terhadap Pengujian Kinerja

Dalam penelitian ini, RAFT dengan SmartBFT pada Hyperledger Fabric v3 diposisikan sebagai RAFT varian, yang dibandingkan dengan RAFT standar pada Fabric v2 dan Fabric v3. Evaluasi kinerja difokuskan untuk mengamati bagaimana penambahan mekanisme SmartBFT memengaruhi throughput, latency, resource usage, dan fault tolerance dalam skenario simulasi pelaporan maladministrasi.

Dengan membandingkan RAFT standar dan RAFT yang diperkuat dengan SmartBFT, penelitian ini tidak hanya menilai efisiensi pemrosesan transaksi, tetapi juga menganalisis trade-off antara kinerja dan ketahanan sistem. Pembahasan pada subbab ini menjadi dasar konseptual untuk interpretasi hasil pengujian pada subbab berikutnya, khususnya dalam menjelaskan perbedaan performa antara Fabric v2 dan Fabric v3 pada kondisi beban transaksi yang bervariasi.
