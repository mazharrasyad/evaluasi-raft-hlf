Bab 4.3

Pembangunan Lingkungan Uji

Repositori penelitian menyediakan empat lingkungan Hyperledger Fabric terisolasi untuk mengevaluasi konsensus RAFT: dua berbasis Fabric v2 dan dua berbasis Fabric v3, masing-masing memiliki konfigurasi standar dan varian. Setiap lingkungan memaketkan skrip otomasi, artefak konfigurasi, serta chaincode pelaporan pada struktur direktori fabric-2/raft-standard, fabric-2/raft-variant, fabric-3/raft-standard, dan fabric-3/raft-variant. Integrasi dengan aplikasi web memastikan status jaringan, penurunan performa, dan hasil simulasi dapat dipantau langsung dari antarmuka yang sama.

  • Skrip network.sh di setiap lingkungan mengorkestrasi pembuatan material kriptografi, kanal, dan deployment chaincode pelaporan maladministrasi.
  • Konfigurasi RAFT dibangkitkan melalui profil ChannelUsingRaft yang disiapkan dalam folder network/configtx, sementara varian BFT tersimpan dalam network/bft-config untuk pengujian ketahanan tambahan.
  • Folder web/src menautkan ke jaringan melalui gRPC Gateway untuk membaca ledger, menjalankan simulasi transaksi massal, serta merekam log kesehatan di web/logs.
Bab 4.3.1

Arsitektur dan Spesifikasi Sistem

Setiap lingkungan testbed mengikuti pola arsitektur yang konsisten: dua organisasi peer (Org1 dan Org2) dengan satu peer produksi, sebuah organisasi orderer dengan TLS aktif, serta dukungan alat bantu untuk CA, CouchDB, dan monitoring. Struktur identitas diturunkan dari berkas organizations/cryptogen sehingga tiap org memiliki satu admin dan satu pengguna standar; contoh konfigurasi Org1 pada jaringan Fabric v2 standar tersedia di fabric-2/raft-standard/network/organizations/cryptogen/crypto-config-org1.yaml yang membatasi jumlah peer menjadi satu per organisasi.

Fabric v2 — RAFT Standar

  • Docker compose utama (compose/compose-test-net.yaml) menyalakan satu orderer orderer.fabric2.standard.com pada port 7050/7053 dan dua peer (peer0.org1.fabric2.standard.com & peer0.org2.fabric2.standard.com) dengan port 7051/9051 serta endpoint operasi 9444/9445.
  • Skrip network.sh mendeteksi otomatis docker atau podman, membersihkan kontainer bertanda raft-standard, dan memanggil configtxgen untuk membangkitkan blok genesis melalui profil RAFT.
  • Chaincode pelaporan (folder chaincode/pelaporan) menyediakan kontrak Catatan Digital yang di-deploy ke kanal fabric2-channel-standard.

Fabric v2 — RAFT Varian

  • Topologi dasar identik, namun komposisi orderer dapat diskalakan menjadi empat node menggunakan compose/compose-bft-test-net.yaml saat opsi -bft pada network.sh diaktifkan.
  • Folder network/bft-config menyiapkan profil SmartBFT untuk fault injection, sementara profil RAFT tetap tersedia melalui network/configtx untuk komparasi langsung.
  • Kanal varian default bernama fabric2-channel-variant dan dioperasikan lewat perintah yang sama pada modul Node.js web/src/network-check.js, hanya berbeda pada domain (variant.com) dan port peer (7052/9151).

Fabric v3 — RAFT Standar

  • Orderer utama orderer.fabric3.standard berjalan pada port 8055/8053 sesuai definisi fabric-3/raft-standard/network/configtx/configtx.yaml, sedangkan peer Org1 dan Org2 masing-masing ter-ekspos di 7153 dan 9153.
  • CLI network.sh memanfaatkan PATH binari Fabric v3 yang dibundel dalam folder bin untuk kompatibilitas configtxgen, peer, dan osnadmin rilis terbaru.
  • Seluruh artefak kriptografi tersimpan di network/organizations dengan layout sama seperti versi v2 untuk mempermudah skrip Node.js berbagi logika akses file.

Fabric v3 — RAFT Varian

  • Domain jaringan menggunakan namespace fabric3.variant dengan penyesuaian port peer (7353 & 9553) serta orderer (8255) sehingga eksperimen dapat berjalan paralel tanpa konflik.
  • Konfigurasi RAFT varian mempertahankan pola paket RAFT v2 (BatchTimeout 1s, MaxMessageCount tinggi) namun memanfaatkan kapabilitas aplikasi Fabric v3 untuk pengujian fitur lifecycle terbaru.
  • Instruksi bring-up dipublikasikan ulang di web/src/network-check.js agar operator dapat menyalin perintah network.sh up dan deployCC langsung dari dashboard.

Pipeline Orkestrasi

Pipeline otomatis dimulai dari pemeriksaan prasyarat (deteksi versi Fabric, ketersediaan CA/cryptogen), dilanjutkan pembangkitan identitas dan kanal melalui scripts/createChannel.sh, kemudian dilengkapi deployment chaincode lewat scripts/deployCC.sh. Modul Node.js web/src/network-check.js menghitung kesehatan jaringan dengan membuka koneksi TLS ke peer, membaca ledger melalui kontrak pelaporan, dan mencatat hasilnya di web/logs/network-check.log.

Bab 4.3.2

Konfigurasi Hyperledger Fabric dan RAFT

Konfigurasi RAFT dihasilkan dari profil ChannelUsingRaft yang didefinisikan pada berkas configtx.yaml masing-masing lingkungan. Selama proses network.sh createChannel, skrip scripts/createChannel.sh memanggil configtxgen -profile ChannelUsingRaft untuk menyusun blok genesis, kemudian menggunakan osnadmin channel join agar seluruh orderer bergabung ke kanal. Variasi parameter RAFT membedakan karakteristik throughput dan latensi antar konfigurasi.

Parameter RAFT — Konfigurasi Standar

  • Fabric v2: BatchTimeout 2 detik, MaxMessageCount 10, PreferredMaxBytes 512 KB, dan AbsoluteMaxBytes 99 MB yang diterapkan pada fabric-2/raft-standard/network/configtx/configtx.yaml.
  • Fabric v3: nilai identik dipertahankan namun orderer terdaftar sebagai orderer.fabric3.standard dengan port 8055, sebagaimana tercatat pada fabric-3/raft-standard/network/configtx/configtx.yaml.
  • Consenters RAFT hanya memuat satu orderer untuk menjaga baseline latency, menjadikan variasi performa lebih mudah diamati saat dibandingkan dengan konfigurasi varian.

Parameter RAFT — Konfigurasi Varian

  • Fabric v2: BatchTimeout dipangkas menjadi 1 detik dengan MaxMessageCount 50 dan PreferredMaxBytes 4 MB (fabric-2/raft-variant/network/configtx/configtx.yaml) untuk mendorong throughput tinggi.
  • Fabric v3: menerapkan skema yang sama pada domain fabric3.variant sehingga analisis difokuskan pada dampak peningkatan versi Fabric terhadap konfigurasi batch agresif.
  • Flag -bft pada network.sh mengganti profil menjadi SmartBFT (network/bft-config/configtx.yaml) sehingga eksperimen dapat menilai dampak failover empat orderer terhadap jalur RAFT varian.

Integrasi Monitoring & Simulasi

Modul web/src/network-check.js menggunakan kredensial TLS dari folder network/organizations untuk membuka koneksi gRPC, menjalankan transaksi GetAllCatatan, dan membaca informasi blok melalui kontrak qscc. Hasil pemeriksaan dan simulasi transaksi massal (melalui web/src/simulation-ingest.js) disimpan di web/logs, menyediakan jejak eksperimen yang seragam untuk seluruh kombinasi RAFT standar dan varian.
